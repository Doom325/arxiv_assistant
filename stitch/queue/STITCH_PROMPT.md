## Visual Direction

### The feeling
This is where a researcher manages what they intend to read. It should feel like
a well-organized personal study — warm, considered, calm. Not a productivity dashboard.
The interface recedes so the content (the papers) leads.

### Color
- Page surface: warm cream or parchment — somewhere in the `#F0EAE0` to `#FAF6EF` range. Never pure white, never cool grey.
- Cards: a subtle step warmer or darker than the page — depth comes from tonal shift, not borders.
- One accent color for all interactive elements (links, buttons, active states). Make it warm and saturated — terracotta, amber, warm red, or something in that family. Use it nowhere else.
- One featured surface for a single hero element (a summary card, a featured paper, a stat block). Choose a deep, rich color — forest green, deep navy, warm charcoal. Use it once and only once on this screen.
- No dark backgrounds. No cool greys. No multiple accent colors.

### Typography
- Page-level headline or section title: a variable-weight serif (Fraunces, Playfair Display, or similar). Mix weights within the headline — light weight for supporting words, heavy weight for the key phrase.
- Body text, metadata, UI labels: a humanist sans-serif (Inter or similar).
- Descriptions and supporting copy: italic.
- Metadata labels (counts, dates, categories): uppercase with generous letter-spacing.

### Space
Be generous with whitespace. More than feels comfortable at first.
Cards need breathing room. Sections need clear separation.
Dense = wrong for this design.

### Surfaces
No structural borders. Cards sit on the page because their background color is different from the page — not because a line is drawn around them.
Shadows, if used, should be warm-tinted and very soft.
Corners: generous — 16px minimum on cards.

### What you should feel free to invent
The layout structure, navigation model, and interaction patterns are entirely up to you.
Consider alternatives to a simple vertical list — the existing app uses one, and that is not the only valid approach. Could priority be spatial? Could reading status be ambient? Could grouping be typographic?
The only constraint is that every capability listed below must be reachable somewhere on screen.

## Capabilities That Must Be Reachable

These are user outcomes. How the user reaches them — what they click, what appears,
what transforms — is your decision.

**Queue overview**
- The user must be able to see at a glance how many papers are in the queue, broken down by source (AI-discovered vs. manually saved), by priority, and by completion.
- The user must be able to see the full list of papers currently in their reading queue.

**Filtering**
- The user must be able to narrow the queue to show only AI-discovered papers, only manually bookmarked papers, or both.
- The user must be able to narrow the queue by read status: unread, currently reading, already read, or skipped.

**Sorting**
- The user must be able to reorder the queue by priority score, by publication date, or by the date added — in either direction.

**Grouping**
- The user must be able to group queue items by publication day, week, or month — or remove grouping entirely.

**Read status**
- The user must be able to mark any paper as unread, currently reading, read, or skipped — without navigating away from the queue.

**Priority override**
- The user must be able to manually set a paper's priority to high, medium, or low, overriding the AI score — and revert that override back to automatic.

**Removal**
- The user must be able to permanently remove a paper from the queue.

**AI actions**
- The user must be able to trigger an AI scan that finds new relevant papers and adds them to the queue.
- The user must be able to trigger a recalculation of all priority scores in the queue.

**Quick preview**
- The user must be able to read a paper's abstract and AI summary without leaving the queue — and navigate to adjacent papers within that same preview session.

**Navigation to paper**
- The user must be able to open a paper's full detail view from the queue.
- The user must be able to open a paper's PDF directly.

**Keyboard and global**
- The user must be able to move focus through the queue using keyboard keys and open the quick preview via keyboard.
- The user must be able to open a global search palette (Cmd/Ctrl+K) from anywhere on this page.
- The user must be able to navigate to any major section of the app using keyboard shortcuts.
- The user must be able to summon a keyboard shortcut reference overlay.
